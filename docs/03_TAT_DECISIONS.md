# 03 TAT DECISIONS — 확정 의사결정 및 작업 규칙

최종 갱신: 2026-09-03

## 문서 역할과 갱신 기준

- 역할: 확정된 결정, 폐기·보류 사항, 금지 규칙의 기록
- 포함: 무엇을 채택·폐기·보류했는지와 그 근거
- 제외: 진행 중 추측, 일회성 실행 로그, 전체 수식 원문
- 갱신: 선택지가 확정되거나 기존 결정을 뒤집을 때, 또는 재사용하면 안 되는 방식이 확정될 때
- 현재 진행 상태는 02, 실행 가능한 수식과 오류 상세는 04에 기록한다.

## 1. 데이터·시스템

- SharePoint를 원본 데이터 저장소로 사용한다.
- Excel 2021은 Power Query·피벗·차트 조회 및 결과 입력 도구로 사용한다.
- 회사 PC에 새 프로그램을 설치하거나 온프레미스 게이트웨이를 사용하지 않는다.
- 현장과 계산서 업체는 서로 다른 마스터 및 Lookup으로 관리한다.
- 분석 관리 단위는 `접수번호 × 분석항목`이며 시료별 배정은 별도 매핑 목록으로 관리한다.

## 2. 의뢰구분

- `미접수`, `측정인`, `과제`만 사용한다.
- `일반`은 사용하지 않는다.
- 미접수↔측정인 전환은 허용한다.
- 과제는 전환하지 않는다.
- 구분변경 시 날짜는 유지하고 새 접수번호를 발급한다.
- `최초접수번호`, `이전접수번호`, `최초의뢰구분`을 보존한다.
- 과제는 과제별 접수 시작번호를 사용하며 기간 검증을 하지 않는다.

## 3. 구분변경 후 파일 처리 — 2026-08-05 자동화 전환

- 앱이 새 접수번호와 관련 SharePoint 표시값을 갱신한다.
- `접수시료항목매핑.접수헤더연결` Lookup은 바꾸지 않는다.
- 매핑의 `제목` 속 기존 접수번호만 신규 접수번호로 치환한다.
- Flow 호출 전 `접수헤더.폴더처리상태`와 `접수구분변경이력.처리결과`를 `처리중`으로 기록한다.
- `TAT_결과파일생성_App`의 변경 모드가 기존 폴더와 Excel 파일명을 변경한다.
- 성공 시 두 상태를 `처리완료`, 실패 시 `처리실패`로 기록한다.
- 과거 `수동처리대기` 및 NAS 수동 변경 안내는 폐기된 이전 설계이므로 새 수식에 적용하지 않는다.

## 4. 상태 관리

- 접수상태 변경은 상세 화면의 상태변경 패널에서 수행한다.
- 2026-08-04 화면에서 확인된 값은 `임시작성`, `접수완료`, `접수취소`이다.
- 과거 설계의 `대기`, `분석 중`, `분석완료`, `보류`, `제외`와 충돌하므로 실제 SharePoint Choice를 다시 확인하기 전 임의로 추가하지 않는다.
- 분석항목별 분석상태는 접수상태와 별도로 관리한다.
- 2026-08-10 SharePoint `접수항목상세.분석상태`에서 확인한 실제 Choice 값은 `대기`, `분석 중`, `분석완료`, `보류`이다.

## 5. 결과 Excel

- 파일명 기본 규칙은 `의뢰번호_접수헤더의 업체 또는 현장`을 기반으로 한다.
- B3에 업체명, B4에 의뢰번호를 기록한다.
- 분석항목은 10개씩 아래로 확장한다.
- 각 블록은 A6:A8의 시험결과·Sample·정량한계 구성을 유지한다.
- 블록 간 여백은 1행이다.

## 6. Power Apps 작업 방식

- 실제 화면명, 컨트롤명, 속성을 먼저 명시한다.
- 수식 변경 시 기존 수식을 찾아 일부를 삽입하라고 안내하지 않는다.
- 기본 제공 형식:

```text
화면 > 컨테이너 > 컨트롤
속성: OnSelect / Items / Text 등
적용: 기존 수식 전체 삭제 후 제공한 전체 수식으로 교체
```

- 전체 수식이 확보되지 않았으면 먼저 사용자에게 현재 전체 수식을 요청한다.
- 기존 로직을 누락하거나 임의로 바꾸지 않는다.
- SharePoint 내부 열 이름과 Lookup 레코드 형식을 추측하지 않는다.
- 화면 설정은 한 번에 따라 할 수 있는 3~5개 단위로 안내한다.

## 7. UI/UX

- 색상보다 화면 구조, 입력 흐름, 상태 인지와 오류 방지를 우선한다.
- `scr접수현황`은 임시작성 전용 화면이 아니라 전체 접수 조회·수정 진입 화면이다.
- 빈 안내 문구도 임시작성 전용 표현을 쓰지 않는다.
- `scr접수상세`의 많은 트리는 기능별 패널 구조이므로 검증 전 합치거나 삭제하지 않는다.
- 명칭 통일, 미사용 컨트롤 삭제, Visible 조건, 노란 경고 정리는 기능 검증 후 수행한다.

## 8. 문서 유지 규칙

- 01: 통합 설계 기준
- 02: 실제 현재 상태, 검증 결과, 오류, 다음 작업
- 03: 확정 의사결정과 금지·보류 원칙
- 04: 실제 수식, 자동화 구조, 오류 로그, 새 대화 인계문
- 작업 결과는 01~04의 역할에 해당하는 문서만 갱신한다. 모든 문서를 기계적으로 함께 수정하지 않는다.
- 오류 발생, 수식 교체, 테스트 성공·실패는 각각 02 또는 04의 갱신 대상이며, 설계나 결정까지 바뀐 경우에만 01 또는 03도 갱신한다.
- 문서에 없는 내용을 기억으로 보완하지 않는다.
- Git은 작업 하나마다 반복하지 않고 세션 단위 체크포인트로 반영한다.
- 기능 검증 완료, 중요 오류의 결론 확정, 세션 종료 전, 사용자 즉시 요청 시 관련 변경을 묶어 `main`에 커밋한다.

## 9. 2026-08-05 신규 저장 검증 확정

- `btn최종저장.OnSelect`의 `TAT_결과파일생성_App.Run()` 호출은 최신 15개 인수 구조를 사용한다.
- Flow 호출부 4곳의 인수·문법 오류가 해소됐다.
- 새 테스트 접수에서 결과 폴더·Excel 생성과 SharePoint 접수헤더 연결이 정상 확인됐다.
- 신규 저장 자동화는 검증 완료로 보고, 다음 검증 대상은 동일 테스트 건의 미접수↔측정인 변경 자동화이다.
- 구분변경 Flow 호출은 15개 인수를 사용한다. 1~5번은 헤더 ID·새 접수번호·새 의뢰구분·현장명·과제명, 6~9번은 `0`, 빈 문자열 3개, 10번은 `"변경"`, 11~14번은 변경 전 구분·접수번호·폴더경로·Excel 경로, 15번은 변경이력 ID로 전달한다.
- 구분변경이 부분 성공한 건은 재실행하지 않는다. Flow가 파일 변경을 완료했는지 검증되지 않은 상태에서 Power Apps의 `.Run()` 응답만으로 성공 처리하지 않도록 후속 수식에서 응답값 또는 Flow 처리결과 검증을 추가한다.

## 10. 2026-08-05 구분변경 안정화 보류 결정

- 신규 생성 직후 Excel Online/Office Script의 일시 잠금이 남을 수 있으므로 변경 Flow는 잠금 오류에 한해 제한 횟수 자동 재시도하도록 향후 개선한다.
- 고정 6분 지연은 모든 실행을 늦추므로 최종안으로 확정하지 않는다. 잠금이 발생한 실행만 재시도하는 구조를 우선한다.
- 접수헤더 경로 4개와 처리상태, 변경이력 처리결과는 Power Apps 응답 후 Patch에만 의존하지 않고 변경 Flow 내부에서 직접 갱신하도록 향후 개선한다.
- 이 구조를 적용하면 Power Automate 실행 기록의 `다시 제출`에서도 실제 파일과 SharePoint 상태가 함께 복구되어야 한다.
- Flow 응답의 결과폴더명과 결과엑셀파일명은 변경 후 폴더 서버 경로의 마지막 구간을 기준으로 생성하며, 변경 전 접수번호를 덧붙이지 않는다.
- 현재 테스트 건 `ENE-260805-016`은 실제 폴더·파일 변경은 완료됐지만 접수헤더 경로 4개가 이전 값인 부분 성공 상태로 기록한다.
- 위 안정화는 향후 작업으로 보류하고, 다음 기능 작업을 먼저 진행한다.

### 2026-08-13 보류 해제 및 적용 결정

- 수동 `지연`·조건·HTTP 복제 분기는 사용하지 않고 `기존폴더이동및이름변경` 작업 자체의 재시도 정책을 사용한다.
- 현재 운영값은 고정 간격 2분, 최대 3회이다. 모든 실행을 선행 지연시키는 고정 6분 대기는 적용하지 않는다.
- Flow 실행 기록 재제출만으로도 접수헤더 경로 4개·처리상태와 변경이력 처리결과가 최종 일치하도록 Flow 내부 갱신을 유지한다.
- 2026-08-13 재제출 복구는 성공했으나 잠금이 이미 해제되어 자동 재시도는 0회였다. 따라서 정책 구성은 확정하되 잠금 지속 상황의 실제 재시도 관찰은 운영 검증 항목으로 남긴다.

## 11. 2026-08-06 분석완료 일괄 처리 화면 요구사항

- 항목별 의뢰번호·시료명·수량을 한 화면에서 조회하는 기능을 다음 신규 기능으로 채택한다.
- 사용자는 처리할 항목을 체크하고 상단에서 분석완료일을 지정한 뒤 버튼으로 선택 항목만 일괄 처리한다.
- 일괄 처리 대상은 화면에서 명시적으로 선택된 항목으로 제한하며, 선택되지 않은 항목의 상태·완료일은 변경하지 않는다.
- 실제 SharePoint Choice 값, 열명, Lookup 구조와 Power Apps 트리를 확인하기 전에는 화면명·컨트롤명·Patch 수식을 확정하지 않는다.
- 이미 분석완료된 항목의 날짜 덮어쓰기 정책과 선택 항목 없음·날짜 미지정 시 동작은 구현 전에 확정한다.

### 2026-08-07 세부 정책 확정

- 기존 `scr분석진행`은 하위 컨트롤이 없는 빈 화면으로 확인됐으므로 분석완료 일괄 처리 화면으로 재사용하며 별도 신규 화면을 만들지 않는다.
- 기존 `의뢰번호 × 시료명 × 분석항목` 행 단위 결정은 시료 수와 분석항목 수의 곱만큼 행이 증가하므로 폐기한다.
- 갤러리 한 행의 데이터 단위는 `의뢰번호 × 분석항목`으로 변경 확정한다.
- 시료는 개별 매핑 행으로 펼치지 않고 `scr접수기본정보`에서 입력해 `접수헤더.'시료명 요약'`에 저장한 값을 표시한다.
- `접수헤더.'시료명 요약'`이 비어 있으면 `-` 등의 대체 문구를 표시하지 않고 공백으로 둔다.
- 기본 표시 열은 `의뢰번호`, `시료명요약`, `분석항목`, `수량`이다.
- 이미 `분석완료`인 항목도 재분석 또는 기존 오선택 정정을 위해 선택할 수 있다.
- 이미 완료된 항목을 다시 실행하면 사용자가 상단에서 지정한 날짜로 분석완료일을 갱신한다.
- 선택하지 않은 동일 의뢰번호의 다른 분석항목 행에는 상태 또는 날짜 변경을 전파하지 않는다.

### 2026-08-10 전체선택 범위 확정

- `scr분석진행`의 전체선택은 SharePoint `접수항목상세` 전체 원본이 아니라 화면의 현재 조회 결과를 대상으로 한다.
- 현재 별도 필터가 없는 단계에서는 `gal분석진행항목.AllItems`에 현재 로드된 행을 선택 대상으로 사용한다.
- `AllItems`는 아직 로드되지 않은 SharePoint 행까지 보장하지 않으므로 이를 SharePoint 전체선택으로 안내하거나 처리하지 않는다.
- 향후 날짜·상태·검색 필터를 추가하면 전체선택은 해당 필터 결과에 포함된 행만 대상으로 유지한다.

### 2026-08-10 분석진행 필터 방향 변경

- 사용자가 의뢰번호를 기억해 입력하기 어려우므로 `txt분석진행의뢰번호검색` 방식은 채택하지 않는다.
- 분석진행 조회는 업체/현장·월·분석항목 조합을 우선해 같은 업체의 월별 입고 건을 구분한다.
- 업체는 기존 `접수헤더.'업체/현장'` Lookup 사용을 우선 검토한다.
- 업무상 입고월과 `접수헤더.의뢰일자`가 동일하다고 확인했으므로 월 필터는 `의뢰일자`의 연·월을 기준으로 한다.

### 2026-08-10 분석진행 위임 안정화 결정

- 운영 데이터 일괄 변경 화면이므로 SharePoint 위임 경고를 데이터 행 제한 내 임시 허용 상태로 유지하지 않는다.
- `접수항목상세`에 화면 필터·표시에 필요한 헤더 및 Lookup 값을 원시 형식 복사 열로 저장한다.
- 신규 접수 저장 시 복사 열을 함께 기록하고 기존 데이터는 Power Automate의 페이지 처리를 사용해 일괄 보정한다.

- 2026년 8월분부터 실제 완료일을 입력할 예정이며 현재 8월분은 아직 공란이다. 과거 공란 허용과 8월 이후 입력 대상은 분리해 관리한다.
- QA·process 등 서로 다른 시료 묶음에 동일 분석항목이 각각 포함될 수 있으므로 접수번호와 분석항목명이 같다는 이유로 원천 행을 중복 제거하거나 병합하지 않는다.
- 이관 시 각 원천 상세 행의 수량·단가·공급가액과 시료 문맥을 보존한다.
- 같은 접수번호 안에서 시료명이 빈 후속 행은 직전의 비어 있지 않은 시료명을 이어받는다. 접수번호가 바뀌면 시료 문맥을 초기화하고 이전 접수 시료명을 절대 승계하지 않는다.
- 새 접수의 첫 유효 시료명 전 공란과 `시료수` 대비 시료명 묶음 수 불일치는 자동 추정·보정하지 않고 오류로 분리한다.

### 2026-09-01 과거 시료수 예외 결정

- 위 시료수·시료명 일치 원칙은 신규 입력·수정 및 2026년 9월 1일 이후 이관 자료에 적용한다.
- 2026년 8월 31일까지의 과거 자료는 접수번호별 원천 행 `수량`의 최댓값을 `접수헤더.시료수`로 사용하며 시료명 묶음 수와 비교하지 않는다.
- 접수별 숫자 `수량`이 하나도 없거나 계산된 최댓값이 0 이하이면 오류로 분리한다.
- 2026년 8월 31일까지는 `접수시료항목매핑`을 생성하지 않고 승계한 시료명을 각 `접수항목상세.배정시료명`에 보존한다.

## 25. 2026-09-02 기존 데이터 의뢰구분 판정·과제 보류

- 원천 `구분`은 분석항목 분류 `일반 / 특정 / 과불`이며 `접수헤더.의뢰구분`으로 이관하지 않는다.
- 기존 데이터 의뢰구분은 접수번호로 판정한다. `ES-DR-` 시작은 `미접수`, `ENE-` 시작은 `측정인`으로 이관한다.
- 우선 이관 범위는 미접수·측정인이다. 두 형식이 아닌 접수번호는 `이관제외`로 분리하고 쓰기를 금지한다.
- 과제 접수는 과제별 접수번호가 있으나 Power Automate 자동화와 관리 기준이 미완성이므로 후속 작업으로 보류한다.
- 2026년 9월 1일부터는 작업본에 정리한 실제 `시료수`를 사용하고 시료명 구조를 검증해 `접수시료항목매핑`을 생성한다.

## 27. 2026-09-03 업체·현장 분리와 현장 지연 생성

- 모든 현장마스터 행을 사용자가 사전에 수작업으로 만드는 방식은 폐기한다.
- 별도 `업체마스터`를 업체 정본으로 두고 `현장마스터`는 업체에 종속된 현장 선택 목록으로 사용한다.
- 업체 선택 직후 기본 현장명은 업체명과 같게 제시한다. 저장 시 같은 업체·같은 현장명이 1건이면 재사용하고 0건이면 생성하며 2건 이상이면 중복 오류로 차단한다.
- 사용자가 현장명을 수정하면 해당 업체 아래 사용자 현장으로 생성한다. 이후 같은 업체 선택 시 기존 현장 드롭다운에서 선택하거나 새 현장을 추가할 수 있다.
- 업체의 기본계산서업체연결을 기본값으로 사용하고 현장별 `계산서 업체 연결` 값이 있으면 이를 우선한다.
- 9월 이관 Flow도 원천 업체에 대응하는 기본 현장을 자동 찾기/생성할 수 있지만, 업체·계산서업체 유일 매칭 검사는 유지한다. 마스터 조회 검사를 단순 우회하지 않는다.
